# Bühnenplaner

German-language stage planner for a single theatre group's private workspace.

Implemented: [slice 01](docs/issue-breakdown.md#01-enter-a-private-workspace-with-password-sign-in), [slice 02](docs/issue-breakdown.md#02-create-and-edit-a-saved-rectangular-stage-layout), [slice 03](docs/issue-breakdown.md#03-inspect-the-saved-layout-in-linked-threejs-views), [slice 04](docs/issue-breakdown.md#04-export-a-frozen-a4-overhead-construction-plan), [slice 05](docs/issue-breakdown.md#05-define-rectangular-door-and-window-wall-types), [slice 07](docs/issue-breakdown.md#07-assign-available-inventory-panels-to-scene-placements), [slice 08](docs/issue-breakdown.md#08-label-panels-for-assembly-and-record-connections), [slice 09](docs/issue-breakdown.md#09-place-weighted-rear-braces-with-measurable-footprints), [slice 10](docs/issue-breakdown.md#10-draw-a-measured-venue-and-trace-a-calibrated-reference), [slice 11](docs/issue-breakdown.md#11-arrange-sets-across-floor-levels-platforms-and-stairs), [slice 12](docs/issue-breakdown.md#12-warn-about-ceiling-and-overhead-obstruction-conflicts), [slice 13](docs/issue-breakdown.md#13-mark-keep-clear-zones-and-show-overlap-warnings), [slice 14](docs/issue-breakdown.md#14-annotate-venue-power-audio-and-routing-possibilities), [slice 15](docs/issue-breakdown.md#15-move-and-rotate-explicitly-grouped-set-pieces), [slice 16](docs/issue-breakdown.md#16-align-walls-with-snapping-guides-and-a-stage-centreline), [slice 26](docs/issue-breakdown.md#26-sign-in-through-pocket-id-and-manage-linked-accounts), [slice 27](docs/issue-breakdown.md#27-invite-members-and-recover-passwords-through-brevo), and [slice 28](docs/issue-breakdown.md#28-protect-editing-with-exclusive-leases-and-stale-write-checks). After sign-in, editors can create a production with a rectangular venue, a venue adaptation and a scene, place 1200 × 2400 × 28 mm walls in a millimetre top-down plan, inspect the same layout in a linked Three.js view, undo or redo session edits, reload the autosaved layout, and export a named frozen A4 construction plan at a fixed 1:50 scale. Scenes can define reusable wall types with rectangular openings that agree in the plan, 3D view, and frozen PDFs. Weighted rear braces can be placed with adjustable millimetre footprints for clearance planning. Editors can draw an irregular millimetre venue outline and calibrate an optional image or PDF trace; frozen plans keep that outline and referenced source file. Walls and braces sit on an explicit supporting surface; permanent platforms and stairs live on the pinned venue version, movable ones on the scene layout, and 3D height comes from that id rather than overlapping polygons. Example millimetres only (400 mm platform, 1200×2000 mm stairs). A venue ceiling and rectangular overhead boxes warn when a wall or brace exceeds local clearance from its supporting surface; saving remains possible and the copy makes no structural certification claim. Labelled keep-clear polygons on a supporting surface warn when walls, braces, or movable pieces overlap them (1 mm contact tolerance); conflicted drafts still save and frozen plans keep the unresolved warnings. Explicit groups of walls, braces, and stairs move and rotate together around the centroid of member centres; connections stay metadata and never form a group. A per-venue stage centreline (point plus orientation in the versioned venue JSON) provides alignment; wall-edge and centreline snapping uses a documented 100 mm / 2.5° tolerance, groups snap as one pose, and Alt or disabling Einrasten bypasses snapping. Mirroring is not included. The workspace inventory stores physical panels with permanent example labels, availability and repair notes; placements can stay unassigned, and duplicate, incompatible or unavailable assignments warn without dropping existing references. Plans show assembly numbers beside permanent panel labels (for example `Position 3 · Platte W12`) and front/back markers; connections and rigging notes are explicit layout metadata. Venues can mark labelled power and audio pins and drawable cable-routing corridors as infrastructure, not as electrical calculations.

## Local setup

Requires Node.js 24 LTS, npm and Docker Compose. Commands run from the repository root.

1. `npm ci`
2. `cp .env.example .env`
3. Generate a signing secret with `openssl rand -base64 48` and put it in `BETTER_AUTH_SECRET` in `.env`. Set the workspace name and the three `BOOTSTRAP_ADMIN_*` values. Use a 12–128 character password. Keep `.env` private; it is ignored by Git.
4. `docker compose up -d --wait db`
5. `npm run db:migrate`
6. `npm run admin:bootstrap`
7. Remove the three bootstrap values from `.env`, then run `npm run dev`.
8. Open <http://localhost:5173> and sign in with the administrator account.

Bootstrap runs only as an explicit command. It atomically creates an identity, password account, workspace and administrator membership. Repeating the command for the existing administrator changes nothing, including the password. Once a workspace exists, bootstrap refuses to add or promote other users. There is no public registration or bootstrap HTTP endpoint.

The Compose file is for local development only. Its database binds to loopback and persists in a named Docker volume. `docker compose stop` stops it without deleting data. Actual deployment and CapRover configuration remain later work.

Each run creates a uniquely named database, applies migrations twice, and removes that database afterwards. Tests do not reset the application database. Inventory tests cover usable stock excluding unavailable panels, unassigned placements remaining valid, duplicate/incompatible/unavailable assignment warnings that keep the stored reference, create/list/assign/unassign with viewer and cross-workspace denial, and the browser workflow that assigns an example panel, shows a stock warning, and reloads the assignment. Assembly tests cover left-to-right numbering from the audience that stays put after a later move, connections that do not change coordinates, save/reload of numbers, connections and rigging notes, and frozen PDFs that keep issued labels and the manual-verification notice.

`npm audit` currently reports four moderate findings through Drizzle Kit's legacy esbuild loader. They also appear with `--omit=dev` because Better Auth declares Drizzle Kit as an optional peer. This application uses the loader for migration tooling and does not run the affected esbuild development server. The findings remain unresolved; do not use an automatic downgrade of Drizzle Kit as an audit fix.

## Structure and choices

- `src/client`: React 19 with Vite 8, German UI, same-origin API access. React is a small browser shell here; layout documents, millimetre geometry and the command stack live in `src/shared` so they stay independent of rendering. Coordinates are millimetres with a centre-anchored wall, origin at the audience-left front of the venue, +x audience-right, +y away from the audience, and positive rotation counterclockwise. Vite's supported React integration and Node requirements are documented in the [official Vite guide](https://vite.dev/guide/).
- `src/shared/assembly.ts`: assembly numbers and panel connections live in the versioned layout JSON. Numbers are assigned from the audience's left-to-right view (`+x` audience-right, looking toward `+y`) and then stick as explicit `assemblyNumber` metadata; later moves do not renumber them. Connections record which walls join and never move neighbouring panels. Connection compatibility is a crew check; the planner does not test hinge geometry.
- `src/client/editor` and `src/server/productions`: top-down SVG editing with a 500 ms revision-checked autosave. Pending, saved, failed and conflict states stay visible; a 409 or 423 leaves the local draft intact. Undo history is session-only. Exclusive editing leases live in `src/server/productions/leases.ts`. The browser sends a heartbeat every 15 seconds; the server expires an abandoned lease after 45 seconds (three missed heartbeats). The same lease module covers scene plans, future venue-record writes, and workspace inventory writes (`inventory` kind, resource id = workspace id). Concurrent collaborative editing is out of scope.
- `src/shared/groups.ts`: explicit groups in versioned layout JSON. The documented pivot is the centroid of member centres in millimetres; positive rotation is counterclockwise, matching walls. Walls are required members; braces and stairs share the same pose transform. Movable platforms are not group members. Connections never auto-group.
- `src/shared/snapping.ts`: millimetre wall-edge and stage-centreline snapping with a documented 100 mm distance and 2.5° common-angle tolerance. Groups translate as one pose so members keep relative offsets. Alt or disabling Einrasten bypasses snapping. The centreline (a point plus orientation) lives in versioned venue JSON. Mirroring is out of scope.
- `src/shared/keepClear.ts`: labelled keep-clear polygons tied to a supporting surface. Overlaps with walls, braces, and movable platforms/stairs on the same surface warn in the editor and as `unresolvedWarnings` on a frozen snapshot. Contact uses a documented 1 mm tolerance. Example millimetres only.
- `src/shared/overhead.ts`: venue ceiling height and axis-aligned rectangular overhead boxes. Clearance uses the object's supporting-surface elevation; conflicts warn in the editor and frozen PDF (`kein statischer Nachweis`) without blocking save. Example millimetres only.
- `src/shared/levels.ts`: supporting surfaces (audience floor plus platforms), stairs that connect two surfaces, and placement diagnostics when a wall or brace has no surface or sits on an ambiguous edge. Permanent platforms/stairs are venue JSON; movable ones are layout JSON. Geometry stays in venue-version and scene JSONB (no extra migration).
- `src/server/inventory` and `src/shared/inventory.ts`: workspace-scoped wall-type catalogue and physical panels. Scene placements keep an optional `panelId`; per-scene `layout.wallTypes` are unchanged. Compatibility is same type id, or same outer millimetres plus matching rectangular openings (opening ids ignored). The group has reported 29 panels (20 plain, 6 door, 2 window, 1 arch). Editor fixtures use example labels such as `Beispiel-P01` and example rectangular door/window openings; they are not real panel IDs. The arch panel is 250 mm thick; its opening profile is not recorded here (slice 06).
- `src/server/exports`: named frozen construction-plan revisions. PDFKit draws a vector A4 overhead at a documented 1:50 scale from the frozen snapshot (design, resolved wall corners, and venue information). Generated files live behind a local-filesystem storage interface; PDF bytes are not stored in JSONB. Rendering runs in a child process so it stays off the API event loop. Failure can be retried from the same snapshot.
- `src/server/identity`: Better Auth identity/session integration, private bootstrap, and application-owned workspace authorization. See the [Fastify integration](https://better-auth.com/docs/integrations/fastify) and [Drizzle adapter](https://better-auth.com/docs/adapters/drizzle) documentation.
- `src/server/db` and `drizzle`: PostgreSQL/Drizzle schema and checked-in migrations. Auth identities and workspace memberships are separate relational records; sessions use the database.
- `src/shared/contracts.ts`: Zod REST schemas shared with the browser. Authenticated members can inspect generated OpenAPI at `/api/openapi.json`; Better Auth routes are handled separately.

Dependencies are exact-pinned in `package.json` and `package-lock.json`, with TypeScript 5.9.3. `npm run build` checks all TypeScript, builds browser assets into `dist/web`, and compiles the backend into `dist/server`.

For the built server, set `NODE_ENV=production`, an HTTPS `APP_ORIGIN`, and run `npm start` with `.env` configured. The server then serves the built UI and API together. The application currently trusts only the socket peer for authentication throttling. Trusted reverse-proxy configuration, persistent/shared rate-limit storage, deployment packaging and HTTPS termination must be addressed in the installation slice. Authentication cookies are HttpOnly, SameSite=Lax and Secure when the configured origin uses HTTPS. Membership is read afresh on every protected request.
