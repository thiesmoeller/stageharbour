# Application UI/UX review and streamlining plan

Reviewed 23 September 2026 against the current working tree, including existing uncommitted changes. This is a review and proposed implementation sequence; no application code was changed.

The application has a capable theatre-planning foundation, but its interface makes users learn feature locations, document scopes, and different save mechanisms before they can work confidently. The largest improvement will come from consistent navigation, trustworthy editing feedback, and task-focused workspaces. Visual refinement should support those changes.

## Evidence and limits

Built the current application successfully with `npm run build`. Used the existing browser-test server with its disposable database and test administrator. Inspected sign-in, the empty workspace, production creation, scene placement and properties, the object library, export controls, venue browsing and editing, the sheet editor, and reload behavior. Captured desktop at 1440 × 900, tablet-sized desktop at 1024 × 768, and mobile-sized desktop at 390 × 844. The main browser walkthrough reported no page JavaScript errors.

These are Chromium viewport checks, not physical touch-device tests. Membership, account linking, recovery, inventory, import calibration, and conflict states were inspected in source and existing tests; their complete workflows were not rerun. No crew usability sessions, screen-reader audit, contrast audit, generated-PDF comparison, or performance benchmark was performed. Findings below distinguish observed behavior from source inspection and proposals.

Screenshots: [production overview](ui-ux-review/production-overview.png), [scene desktop](ui-ux-review/scene-desktop.png), [scene tablet](ui-ux-review/scene-tablet.png), [scene mobile](ui-ux-review/scene-mobile.png), [venue desktop](ui-ux-review/venue-desktop.png), [sheet editor](ui-ux-review/sheet-editor.png). Some captures precede completion of the asynchronous 3D render; blank 3D captures are not treated as rendering defects.

Preserve the useful foundations: linked plan/3D geometry, undo/redo, precise millimetre entry, scene autosave, immutable venue versions, explicit adaptation updates, frozen construction revisions, role permissions, lease protection, and draft recovery. Desktop editing already uses the available viewport well, and the sampled narrow screens had no horizontal page overflow.

## Prioritized findings

P1 means resolve before considering the streamlined experience ready. P2 means address in the corresponding workflow redesign. These are impact priorities, not measured incident frequencies.

| ID | Priority | Finding and evidence | Required change |
| --- | --- | --- | --- |
| U01 | P1 | **The saved indicator can misrepresent visible edits.** Reproduced: select a wall at X=4000, type 4500 without pressing `Übernehmen`; header remains `Gespeichert`, Back is enabled, and reopening restores 4000. `WallForm` uses local/uncontrolled fields while document dirty state excludes those fields. | Track pending inspector edits. Commit valid changes consistently, or display `Nicht übernommene Eingaben` with Apply/Cancel and protect selection changes, navigation, export, and reload. `Gespeichert` must never imply that unapplied visible inputs are durable. |
| U02 | P1 | **Locations are not addressable.** Scene and venue selection live in React state. ## Proposed information architecture

Use three primary destinations: **Produktionen**, **Spielstätten**, and **Bibliothek**. Put **Mein Konto** in the account menu and **Verwaltung** behind administrator permissions. A production opens a detail page containing its venue adaptations, scenes, and issued documents. A scene opens a focused editor with a breadcrumb and scene switcher. Venue geometry and venue-owned sheet templates remain associated with the venue. Global library organization must keep reusable definitions distinct from physical stock.

| Destination | Contents | Primary action |
| --- | --- | --- |
| Produktionen | Searchable productions, recently opened work; production detail with adaptations, scenes, and documents | Neue Produktion; within an adaptation, Neue Szene |
| Spielstätten | Actual plan previews, dimensions, version and usage summaries; geometry and Blattvorlagen | Neue Spielstätte |
| Bibliothek | Objektvorlagen, Plattenbestand, Szenenvorlagen; model import/catalog within object templates | Context-specific creation/import |
| Mein Konto | Linked sign-in and account actions | Account-specific action |
| Verwaltung | Members/invitations, branding, activity history | Mitglied einladen where applicable |

Do not add another dashboard unless testing shows a task it solves. The production list can provide a useful default landing page with recent work and a clear next action.

## Editor and interaction contract

The desktop scene and venue editors should share one shell: a compact scope/breadcrumb header; document status and history; a grouped editing toolbar; central canvas; selection inspector; and an issues/status area. The shell shares interaction rules while domain-specific tool groups and publication behavior remain explicit.

The default empty scene should explain one action: add an object. After insertion, selection properties replace that prompt. Make `Einfügen` expose walls, braces, platforms, stairs, placeholders, and models together. A visible wall-type dropdown can retain direct insertion of the most recently used type. Advanced catalogue editing should not occupy the default inspector.

Use common property groups: **Position**, **Maße**, **Auflagefläche**, **Aussehen**, and **Aufbau**, showing only applicable groups. Preserve explicit millimetre units and German number handling; do not silently convert persisted geometry. Keep assembly number and permanent panel label distinct. Mixed selection must explain which fields affect every selected object and which actions are unavailable.

Choose one field-commit policy and enforce it across inspectors. A recommended starting point is validated commit on Enter/blur, with Escape restoring the prior value and one coherent undo step. Incomplete numeric input must remain editable without invalid geometry or premature autosave. If atomic Apply forms remain necessary, pending fields need their own visible status and navigation protection. Persist recoverable drafts with a scene/venue revision and account/workspace identity, without bypassing leases or silently overwriting newer server versions.

Keep edition and persistence states separate: `Nur Ansicht`, `Bearbeitet von …`, and `Bearbeitung verfügbar` describe permission; `Änderungen offen`, `Speichert …`, `Gespeichert`, and `Speichern fehlgeschlagen` describe the document. Venue drafts additionally distinguish saved draft from published version if draft persistence is introduced. Publication and adaptation adoption should show which production/scenes will be affected before committing.

On narrow screens, use a single canvas and a collapsible properties sheet. Offer both view modes without forcing users to scroll past one to reach the other. Preserve canvas position and selection when opening properties or switching 2D/3D. Keep advanced editing reachable; validate whether the crew primarily needs review/download or full editing on phones before reducing functionality.

## Visual and accessibility baseline

Use a restrained neutral canvas with the existing green accent, a consistent spacing scale, readable type, and a small set of component patterns. Proposed defaults are 14–16 px body/form text, 12 px minimum secondary labels, 32–36 px desktop controls, and 44 px touch targets. These are product design targets, not claims that WCAG mandates those font sizes or all those control sizes.

Target WCAG 2.2 AA. Its target-size criterion generally requires 24 × 24 CSS px or applicable exceptions, including spacing; larger touch controls are a deliberate usability choice. Also verify focus visibility, non-drag alternatives, keyboard completion, error association, text zoom/reflow, and accessible authentication. [W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/), [target-size guidance](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum).

Use actual modal behavior where the UI declares a modal: focus entry, contained tab navigation, Escape, background inertness, and focus restoration. Nonmodal inspectors/drawers should have predictable focus and dismissal without unnecessarily trapping the user. [W3C dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/).

Progressive disclosure should expose frequent tasks and reveal specialist settings in context. Avoid replacing the current long panels with deeply nested menus; discoverability and status visibility matter as much as visual simplicity. [Nielsen Norman Group: progressive disclosure](https://www.nngroup.com/articles/progressive-disclosure/), [usability heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/).

## Implementation sequence

| Phase | Concrete deliverable | Exit criteria |
| --- | --- | --- |
| 1. Establish editing trust | Fix U01; prevent read-only navigation from creating template drafts; document and implement pending-field, save, publication, and conflict behavior | Unapplied edits cannot silently disappear; save status accurately reflects visible input; opening sheet layout alone does not dirty a venue; failure/lease-loss retains recoverable work |
| 2. Build navigation and shared UI foundations | Stable routes, shared page/editor shell, initial tokens and dialog/form primitives; move account/admin out of planning | Reload/deep link/Back/Forward preserve location; authorization remains enforced; leaving dirty work has one consistent flow; administration has a dedicated destination |
| 3. Streamline production and library work | Production detail, explicit new-scene flow, contextual action menus, searchable libraries and venue list, consistent terminology and previews | A new user can create a production, reuse a venue, add a second scene, and distinguish stock from templates without instruction |
| 4. Unify editors and responsive behavior | Shared tool grouping, contextual inspector, visible type selection, issues panel, narrow-screen canvas/drawer behavior | Equivalent operations behave consistently in venue/scene and 2D/3D; selected objects remain visible while editing; keyboard/touch paths are usable |
| 5. Complete construction-document workflow | Consolidated export workspace, template/page/frame controls for supported output, real preview, revision history and artifact rendering | Chosen scope, paper, scale, layers, frames, and views match the generated frozen PDF; existing revisions remain unchanged and downloadable |
| 6. Refine and release | Complete visual migration, content polish, measured loading improvements, role-specific acceptance and crew walkthrough | All P1 items closed; agreed journey and accessibility criteria met; no regression in geometry, permissions, leases, version adoption, or frozen output |

Implement these as small vertical changes behind the existing domain model. Establish shared components as their first workflows migrate; avoid a separate application-wide rewrite before users receive improvements. Plan estimates only after the export/template gap and draft-persistence work have been sized.

## Final review plan

1. **Record the baseline.** Use fixtures for an empty workspace, several productions with multiple venue adaptations, and a dense scene. Include administrator, editor, viewer, another editor's lease, pending edits, network failure, and a newer server revision. Capture task completion, time, wrong turns, assistance, and data-loss incidents. The measurements in this review are layout observations, not usability success rates.
2. **Validate navigation and terminology first.** Run task-based tree tests and a clickable flow with 5–6 representative crew members across design, build, and administration. Ask them to find a scene, add a second scene, manage a physical panel, reuse a template, update a venue, and retrieve an issued plan. Investigate repeated confusion before implementing the new navigation broadly.
3. **Review one complete editor journey.** Create production → reuse venue → insert wall type and prop → move numerically and by pointer → assign panel → undo → leave/reopen → resolve a warning → issue a plan. Include the reproduced unapplied-field case, multi-selection, cancelled placement, failed autosave, lease expiry, and attempted export during pending input. Verify persisted results, not just visible button states.
4. **Review every layout and input mode.** Check 1440 × 900, 1280 × 720, 1024 × 768, and 390 × 844; add actual touch devices, keyboard-only use, 200% zoom, and screen-reader checks. Verify focus is visible, dialogs return focus, menus have keyboard access, primary actions stay reachable, and properties do not require scrolling past two canvases. Add 320 CSS px reflow checks for surrounding forms and navigation while treating the spatial canvas appropriately.
5. **Review document scope and artifacts.** Publish a venue version and explicitly adopt it into an adaptation; confirm unaffected adaptations keep their pin. Compare export preview with actual A4/A3 output, scales, page count, layers, views, warnings, and frame placement. Download an older revision after subsequent edits and confirm it is unchanged. Verify viewers can retrieve issued documents without seeing misleading creation actions.
6. **Set and apply release gates.** Proposed usability targets: at least 90% unassisted completion across the agreed core task attempts, no repeated critical confusion about save/scope, and zero silent edit-loss cases. Report raw participant/task counts because a small cohort is directional evidence. Require all P1 findings resolved, no known critical accessibility barriers in core journeys, and passing targeted browser/integration checks for changed behavior. Run a final crew walkthrough, document any remaining P2 issues with owners, and review the pilot after two weeks of real use.
